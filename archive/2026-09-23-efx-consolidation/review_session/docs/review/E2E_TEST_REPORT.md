## Defects found (kept as failing assertions)

1. **Credit-card requested limit never reaches the Finance checklist.** `getWorkflowContext()` (EmailUtils.js, Initial Requests branch ~:175-330) maps `CC USA/CAN/HD` but not `Limit USA/CAN/HD` (IR cols 31/33/35), so `triggerSpecialists` (ITSetupHandler.js:483-485) always writes *"Apply for USA card — Requested limit: Standard"* even when the request carried `creditCardLimitUSA: '2000'`. (`getITContextData` does map the limits, but `triggerSpecialists` reads `getWorkflowContext`.) Inherited from dev/prod; not EFX-specific.
2. **Status-change approval routes the final "Status Change Approved" (and `managerEmail` in every approval email) to the OLD manager.** PositionChangeHandler.js:426 tests `changes.includes('Reporting Manager Change')`, but the form and the contract (`multi.changeType`) send `'Manager Change'`, so `mgrNewEmail` falls back to `mgrOldEmail` and the new manager is never on the recipient list (they only get the *Incoming Transfer* item). Already flagged in the `position_change_request` contract notes; the assertion proves it.
3. **Fleetio "Access Update" and "Access Removal" collapse into one task.** `ActionItemService.createActionItem` (ActionItemService.js:64-80) dedups on `workflowId + category + formType`; PositionChangeHandler.js:235 and :273 both create `Fleet/fleetio`, so when a status change adds *and* removes Fleetio the removal checklist is silently dropped while both emails are still sent (pointing at the same task). Same hazard exists for any two same-category/same-formType items created in one approval.

## Oddities observed (documented, not failed)

- `submitITConfirmation` never closes the **"IT Confirmation" action item** it was preceded by (ITConfirmationHandler.js:44-266); it stays Open and is only harmless because `getRequiredSpecialistCats` excludes it and StateSync skips it. The suite closes it via `n8n_closeTask` after completion to prove it is non-blocking.
- **JR Title is non-blocking**: `getRequiredSpecialistCats` (ActionItemService.js:479-486) does not add `'JR Title'`, so a New Hire can reach `Complete` with the JR task Open (documented in `docs/mapping/JR.md` §2). Scenario 5 still proves the alias close triggers completion when it is the last task.
- The **`submit` Raw Log event of every create has an empty `Workflow ID`** (`rawLog` runs before `createWorkflow`); n8n must correlate creates via the `result` event (New Hire) or the alias response (Equipment / Termination / Change have no `result` event).
- **Handlers mutate their payload** (`workflowId`, `formId`, `timestamp` are added to the object passed to `submitInitialRequest` / `submitTerminationRequest` / `submitPositionChangeRequest`). **Mitigated in the fork:** `n8nSubmit_` hands handlers a copy, so an n8n retry with the same item is now safe (the suite asserts the caller's object is untouched).
- **Workflow-id collision** (`generateWorkflowId` = second timestamp + 3 random digits) surfaced once as a flake in scenario 2. **Fixed in the fork:** `createWorkflow` regenerates until the id is unused (defect #18).
- **`CHANGE_` IT Setup writes `IT Results` twice** (ITSetupHandler.js:312 + ActionItemService.js:250 belt-and-suspenders) → two rows for one workflow.
- **30-second `createWorkflow` idempotency** (WorkflowManager.js:91-104) returns the same workflowId but `submitInitialRequest` still appends a second `Initial Requests` row and re-sends both emails.
- **`it_confirmation` shape sensitivity**: the change-diff compares `purchasingSites`/`systems`/`equipment` as arrays; a CSV string for `purchasingSites` is treated as "cleared" and emits a spurious *Information Updated* to requester+manager (the write-back itself handles the string). n8n must send arrays here.
- *Assets Returned* emails on Assets-task closure depend on checklist statuses being `Collected` (not `Complete`); `n8n_closeTask` supports that via `checklist`.
- Authorization is **principal-based** (`Actor.principal()` = the real session / impersonated bot); the actor object only attributes rows and Raw Log entries. Under the mock the principal is the admin (`dbinns@team-group.com`), so HR/IT/approval steps pass; the session-swap block shows the denial path.
- `EMAIL_REDIRECT_ALL` from the mock config means the redirected-`to`/`[TEST]` path is what the run exercised, not real routing.
